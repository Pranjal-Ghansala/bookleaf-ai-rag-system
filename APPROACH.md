# BookLeaf Assignment — Approach and Trade-offs

I approached the Author Support & Communication Portal by prioritising the complete support-ticket workflow across both author and admin roles. The author experience focuses on account-specific book and royalty visibility, ticket creation, and a message thread. The admin experience focuses on triage: filtering the queue, reviewing AI-suggested category and priority, assigning work, changing status, recording private notes, and preparing a response for human review.

The application uses React/Vite for the interface, an Express REST API for business logic, MongoDB/Mongoose for persistence, JWT for authentication, and bcrypt for password hashing. Role checks are enforced on the backend rather than relying only on frontend visibility. The seed script validates that the supplied assignment dataset contains 10 authors and 18 books and imports those records so the main book and royalty edge cases can be demonstrated.

For AI, I chose Gemini through the Google GenAI SDK. Classification is requested as constrained JSON and validated against allowed categories and priorities. Draft responses are generated from the BookLeaf policy text plus the relevant ticket/book facts and a limited recent message history. This keeps prompts focused and avoids resending the full conversation on every draft request. AI failures do not block ticket creation: classification falls back to a safe default, while the response workflow supplies a manual starter. Admins can edit the draft before it is sent, keeping a human in control of author-facing communication.

I made pragmatic trade-offs to keep the assignment manageable. Author ticket updates use five-second polling instead of a persistent WebSocket/SSE connection. Attachments are represented in the UI only, as the brief permits. The policy knowledge base is included directly in the prompt; this is knowledge-base-grounded prompting, not a full vector-search RAG implementation. These choices reduce infrastructure complexity, but they are not the final design I would choose for a high-volume production system.

Before production, I would add automated unit and integration tests, rate limiting, audit logs, monitoring, stronger admin provisioning, and more comprehensive security review. I would also move policy content into a versioned searchable knowledge store, retrieve only relevant policy passages for each ticket, show those sources alongside AI drafts, and evaluate classification accuracy and response quality against a reviewed test set. Finally, I would replace polling where appropriate with SSE/WebSockets and improve attachment handling with secure file storage and validation.

The main priority was a usable end-to-end workflow with backend-enforced access control, graceful AI failure handling, and clear opportunities for an operator to review AI output rather than sending it blindly.
